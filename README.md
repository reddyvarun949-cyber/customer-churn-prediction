# Customer Churn Prediction

**Methods practised:** classification models and metrics (B1 Module 08) and model evaluation & optimisation
(Module 10): stratified K-fold cross-validation, ROC-AUC / PR-AUC / precision / recall / F1, `GridSearchCV`,
learning curves, precision-recall curves and choosing a decision threshold from business costs.
Also uses preprocessing pipelines (Module 05) and saving a model behind an API (Module 13).

## Problem statement

SwiftNet, a fictional broadband and mobile company, loses customers every month. The retention team can give a discount
to customers who are about to leave, but each offer costs money. Given a customer's contract, tenure, bill, services,
payment method and recent complaints, predict the **probability that the customer cancels (churns) next month**, and
decide **whether to contact them with an offer**.

**Expected result:** a model that ranks churners clearly better than a "never churns" baseline, a decision threshold
chosen from a simple cost table (offer cost vs value of a saved customer) instead of the default 0.5, an honest
test-set evaluation, and an API + web page for one customer or a batch of up to 100.
(The build run's actual numbers are in `VERIFICATION.md` and the executed notebook.)

## Dataset

Synthetic data generated by `data/generate_data.py`. Churn follows realistic rules (month-to-month contracts, new
customers, complaints, fibre without tech support and electronic-check payments raise churn; long contracts and long
tenure lower it) plus randomness. About 19% of customers churn, so the classes are imbalanced. A classic real-world
problem is included on purpose: `total_charges` is stored as **text** and is blank for brand-new customers. See
[data/DATA_DICTIONARY.md](data/DATA_DICTIONARY.md). The target column is `churn` (Yes/No).

## What the notebook does

1. **Clean:** convert `total_charges` to numbers; the blanks all belong to customers with tenure 0, so they become 0
   (not "unknown"); drop duplicate rows; convert the target to 1/0.
2. **Explore:** churn rate by contract, tenure, complaints, internet service, tech support, payment method, etc.
3. **Split** 80/20 with `stratify=y`; build a `ColumnTransformer` pipeline (impute + scale / impute + one-hot).
4. **Compare** a baseline, logistic regression, random forest and HistGradientBoosting with stratified 5-fold CV on
   five metrics. In the build run the simplest model, logistic regression, had the best PR-AUC.
5. **Tune** the best family with a small `GridSearchCV`, and draw a **learning curve**.
6. **Choose the threshold** with out-of-fold predictions and a business cost table: offer costs ₹500, a saved customer
   is worth ₹4,000, 30% of contacted churners stay. The threshold with the highest expected profit is stored.
7. **Evaluate once on the test set**, compare the profit of "contact nobody / everyone / threshold 0.5 / business
   threshold", analyse missed churners, and compute permutation importance.
8. **Save** the pipeline and `model_info.json`, reload and check, and list limitations.

## How to run (three terminals)

**1. Python environment and notebook** (from this project folder):

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python data/generate_data.py                                  # optional: the CSV is already included
jupyter notebook notebook/Customer_Churn_Prediction.ipynb     # Run All: this creates models/
```

The trained model is already included in `models/`, so you can skip straight to step 2 if you only want the app.

**2. Backend API** (same environment, from this project folder):

```bash
python backend/app.py                 # http://localhost:5000
python -m unittest discover -s backend -p "test_*.py" -v    # optional: run the tests
```

Try it without the frontend:

```bash
curl http://localhost:5000/api/health

curl -X POST http://localhost:5000/api/predict -H "Content-Type: application/json" \
  -d '{"tenure_months":2,"contract_type":"Month-to-month","monthly_charges":1050,"total_charges":2100,"internet_service":"Fiber optic","tech_support":"No","payment_method":"Electronic check","paperless_billing":"Yes","num_complaints_6m":3,"avg_data_gb":90,"senior_citizen":0,"city_tier":"Tier 1"}'

curl -X POST http://localhost:5000/api/predict-batch -H "Content-Type: application/json" \
  -d '{"customers":[{"customer_id":"C-1","tenure_months":60,"contract_type":"Two year","monthly_charges":700,"total_charges":42000,"internet_service":"DSL","tech_support":"Yes","payment_method":"Bank transfer (automatic)","paperless_billing":"No","num_complaints_6m":0,"avg_data_gb":45,"senior_citizen":0,"city_tier":"Tier 2"},{"customer_id":"C-2","contract_type":"Weekly"}]}'
```

The second batch row is invalid on purpose: the response contains a result for row 1 and a list of field errors for
row 2, instead of failing the whole request.

**3. Frontend** (needs Node.js 18+):

```bash
cd frontend
npm install
npm run dev                           # open http://localhost:5173
```

If the API runs somewhere else, copy `.env.example` to `.env` and change `VITE_API_URL`. If the frontend runs on a
different address, start the backend with `FRONTEND_ORIGIN=http://that-address python backend/app.py`.

The page has two parts: a **form for one customer** (shows the churn probability, the decision and a recommended
action) and a **batch section** where you paste a JSON list or upload a CSV file. The CSV is read in the browser with a
simple comma split (first line = column names, same names as the API fields, optional `customer_id`; quoted values
containing commas are not supported) and sent to the API as JSON. The frontend was not run in the build environment —
see `VERIFICATION.md`.

## Architecture and request flow

```
 Browser (React)                          Flask API (backend/app.py)                     models/
 ───────────────                          ──────────────────────────                     ───────
 page opens ─── GET /api/options ──────▶  info loaded at start-up  ◀───────────────────── model_info.json
            ◀── categories, ranges, threshold, business assumptions
 form submit ── POST /api/predict ─────▶  1. parse JSON (400 if not JSON)
   {tenure_months: 2, ...}                2. validate every field (422 + per-field messages)
                                          3. one-row DataFrame → pipeline.predict_proba ◀── churn_model.joblib
            ◀── 200 {churn_probability, will_churn, decision, recommended_action, threshold, ...}
 CSV/JSON ──── POST /api/predict-batch ─▶ 1. parse JSON, check it is a list of 1-100 customers (422 otherwise)
   {customers: [...]}                     2. validate each row separately; bad rows get their own field errors
                                          3. ONE predict_proba call for all valid rows
            ◀── 200 {results: [{row, customer_id, ok, ...}], summary: {total, valid, invalid, to_contact}}
 shows the result card / results table, or the error messages
```

- The model is **trained once in the notebook** and loaded **once when the API starts**. Requests only call
  `predict_proba`.
- The **threshold lives in `model_info.json`**, not in the code. If the business assumptions change, rerun section 9 of
  the notebook and restart the API.
- Recommended actions: probability ≥ max(0.7, threshold + 0.25) → personal call + discount; ≥ threshold → send the
  discount; ≥ half the threshold → watch list (survey, check complaints); otherwise no action.

### API reference

| Method | Path | Request | Success response | Errors |
|---|---|---|---|---|
| GET | `/api/health` | — | `{"status": "ok", "model": "...", "threshold": t}` | — |
| GET | `/api/options` | — | `{"categories", "numeric_ranges", "optional_fields", "threshold", "business_assumptions", "model", "test_metrics", "max_batch"}` | — |
| POST | `/api/predict` | JSON with the 12 customer fields | `{"churn_probability", "will_churn", "decision", "recommended_action", "threshold", "model", "note"}` | 400 body not JSON; 422 `{"error", "fields": {field: message}}` |
| POST | `/api/predict-batch` | `{"customers": [ ... ]}` (or a plain list), 1-100 items | `{"results": [{"row", "customer_id", "ok": true, ...prediction} or {"row", "customer_id", "ok": false, "fields"}], "summary", "threshold", "model"}` | 400 body not JSON; 422 not a list / empty / more than 100 |

Validation rules: all fields required except `avg_data_gb` (filled with the training median) and `total_charges`,
which may be blank **only** when `tenure_months` is 0 (it then becomes 0, the same rule as in the notebook); numbers
must lie inside the training ranges; `tenure_months` and `num_complaints_6m` must be whole numbers; `senior_citizen`
must be 0 or 1; categorical values must be ones the model has seen; `tech_support` must be "No internet service"
exactly when `internet_service` is "No internet".

## Ideas to extend

- Change the business assumptions (offer cost, customer value, success rate) and see how the best threshold moves.
- Calibrate the probabilities with `CalibratedClassifierCV` and compare a calibration plot before and after.
- Try `RandomizedSearchCV` with a wider grid for HistGradientBoosting and check whether it can beat logistic regression.
- Add a "download results as CSV" button to the batch table.
- Log every batch request to see how the share of high-risk customers changes month by month (simple monitoring).

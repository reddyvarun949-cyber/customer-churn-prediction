# Data dictionary — telecom_churn.csv

Synthetic data for a fictional Indian broadband + mobile provider ("SwiftNet"), generated by `generate_data.py`
(seed 42). 5,000 unique customers plus 30 duplicated rows added on purpose (5,030 rows in the file).
Licence: created for this course; free to use and share.

Each row is one customer at the end of a month. **The target `churn` says whether the customer cancelled during the
NEXT month.** About 18.8% of customers churn (948 of the 5,030 rows), so the classes are imbalanced.

| Column | Type | Description | Values / range | Missing / issues |
|---|---|---|---|---|
| `customer_id` | text | Customer identifier. Not a feature. | CUST-00001 … CUST-05000 | 30 duplicated rows |
| `tenure_months` | integer | Months as a customer (0 = joined this month) | 0–72 | none |
| `contract_type` | category | Contract length | Month-to-month, One year, Two year | none |
| `monthly_charges` | number | Current monthly bill in rupees | 199–1,546 | none |
| `total_charges` | **text** (holds a number) | Total paid so far in rupees | 0–about 1,08,800 | **132 rows are a blank `" "`** — all of them customers with tenure 0 (not billed yet), so the correct value is 0 |
| `internet_service` | category | Internet plan | Fiber optic, DSL, No internet | none |
| `tech_support` | category | Tech-support add-on | Yes, No, No internet service (only when there is no internet) | none |
| `payment_method` | category | How the bill is paid | Electronic check, UPI autopay, Credit card (automatic), Bank transfer (automatic) | none |
| `paperless_billing` | category | Bills by e-mail only | Yes, No | none |
| `num_complaints_6m` | integer | Complaints logged in the last 6 months | 0–6 | none |
| `avg_data_gb` | number | Average monthly data use in GB | 0.1–416 | 40 rows (usage meter not reported) |
| `senior_citizen` | 0 / 1 | 1 if the customer is 60 or older | 0, 1 | none |
| `city_tier` | category | Size of the customer's city | Tier 1 (metro), Tier 2, Tier 3 (small town) | none |
| **`churn`** | Yes / No | **Target.** Did the customer cancel during the next month? (the notebook converts it to 1 / 0) | Yes ≈ 18.8% | none |

## How churn was generated

Each customer's churn chance comes from a logistic formula (hidden from the model) plus randomness:

- **Raises churn:** month-to-month contract (strongest), being in the first 3 months, more complaints, fibre internet,
  no tech support, paying by electronic check, paperless billing, higher monthly charges, being a senior citizen,
  living in a Tier 1 city.
- **Lowers churn:** one-year and especially two-year contracts, longer tenure (up to about 4 years).

`total_charges` is roughly `tenure_months × monthly_charges` with ±5% noise (prices changed over time), so it overlaps
strongly with tenure. Knowing the rules lets you check whether the model learned sensible patterns — for example that
contract type and complaints matter far more than data usage.

Missing counts above include the duplicated rows.
